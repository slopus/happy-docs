## Toolchain

| | |
|---|---|
| Rust | pinned in `rust-toolchain.toml` with clippy and rustfmt; rustup installs it on first use. OpenSSL is vendored (for `webauthn-rs`), so the first build needs a C compiler and `perl`. |
| Lean | `elan` reads `proofs/lean-toolchain` (Lean v4.34.0). No packages, no Mathlib. |
| Postgres | `scripts/dev-db.sh` downloads Postgres 18.6 binaries, pinned by version and checksum, for Linux x86_64/aarch64 and macOS arm64/x86_64. No Docker. |

## Repository layout

```text
crates/server/          the only crate (package happy-enterprise)
  src/app.rs            pools, routers, the two listeners, graceful shutdown
  src/tenant/           tenant API: tx.rs (TenantTx), auth.rs, login.rs, mfa.rs,
                        org.rs, members.rs, teams.rs, files.rs, oauth.rs, mcp.rs,
                        ontology/ (schema, objects, validators, events)
  src/management/       management API
  src/ontology/         schema types, value checking, query compilation
  src/validators.rs     the Monty sandbox pool
  tests/                integration tests against a real Postgres
migrations/             sqlx migrations (see migrations/AGENTS.md)
proofs/                 Lean 4 models and proofs
scripts/                dev-db.sh, dev-s3.sh, check.sh, mcp-client-demo.sh
```

## Local database

```sh
scripts/dev-db.sh install          # once: download + verify Postgres into .context/pg/dist
scripts/dev-db.sh start            # initdb on first run, start, create database happy_enterprise
eval "$(scripts/dev-db.sh env)"    # export DATABASE_URL, TENANT_DATABASE_URL, MANAGEMENT_DATABASE_URL
scripts/dev-db.sh psql             # psql as superuser postgres
scripts/dev-db.sh stop | reset     # stop; reset also deletes the data directory
```

The cluster listens only on a unix socket under `.context/pg/run`, with
trust authentication. It is for local use only. `DEV_DB_DIR` moves it (unix
socket paths must stay under about 100 bytes).

## Tests

Integration tests use `#[sqlx::test]`: each test creates a fresh database
through `DATABASE_URL`, applies the migrations, and connects as both runtime
roles, the way the server does. Email goes to an in-memory sender, files to
a temporary directory, DNS lookups to a static resolver, and outbound HTTP
(email providers, S3) to in-process fakes. Tests bind no ports.

```sh
cargo test                        # unit + integration tests
cargo test --test isolation       # one suite
RUST_LOG=warn cargo test ...      # with server logs, for a failing test
```

| Suite | Covers |
|---|---|
| `isolation` | every tenant table, reads and writes across tenants, missing context, the catalog (forced RLS, policies, grants) |
| `auth` | session tokens, external JWTs, agent tokens, audiences, revocation |
| `org` | joining, verified domains, invites, owners and system teams, permissions, files |
| `mfa` | TOTP, WebAuthn, partial sessions, required 2FA |
| `mcp` | discovery, registration, authorization, tokens, refresh, revocation, tools |
| `ontology` | types, versions, schema changes, objects, links, queries, access |
| `validators` | custom validators, escape attempts, resource bombs |
| `live` | event streams, filters, resumption, pruning, limits |
| `limits` | rate limits on login, second factors, OAuth |
| `guardrails` | source checks: who may open an `OrgTx`, where `app.tenant_id` is set, no `SET ROLE` |
| `s3` | `S3Store` against a real S3-compatible server; skipped unless `S3_TEST_ENDPOINT` is set |

`cargo build` and `cargo clippy` need no database: queries use runtime
`sqlx::query*` functions, not compile-time-checked macros.

## Before every commit

```sh
scripts/check.sh   # cargo fmt --check, clippy -D warnings, cargo test, proofs/check.sh
```

The project's rules, enforced in review and partly by `tests/guardrails.rs`:

1. Every security or isolation invariant has a Lean counterpart, listed in
   the [invariant map](/docs/verification/#invariant-map). Change the Rust,
   the Lean model, and the table together.
2. Every new tenant-owned table gets a `tenant_id cuid` column, `ENABLE` and
   `FORCE ROW LEVEL SECURITY`, the standard `tenant_isolation` policy, and
   coverage in `tests/isolation.rs`.
3. Tenant code reaches Postgres only through `TenantTx` (or `PartialTx`).
   Only authentication code opens an `OrgTx`, and only maintenance jobs a
   `JobTx`. Nothing else sets `app.tenant_id`.
4. Tenant queries still filter by `tenant_id` explicitly. RLS is the
   backstop, not the only check.
5. Authentication failures all return the same `401`.
6. Permission checks go through `TenantTx::permitted`, `require`, and
   `require_owner`.
7. All ids are cuid2, generated by the application.

## S3 tests

`scripts/dev-s3.sh` runs the Versity S3 Gateway (POSIX backend, SigV4
checked) on `127.0.0.1`:

```sh
scripts/dev-s3.sh install   # once
scripts/dev-s3.sh start && eval "$(scripts/dev-s3.sh env)" && cargo test --test s3; scripts/dev-s3.sh stop
```

## End to end with a real MCP client

`scripts/mcp-client-demo.sh` starts the server on `localhost:18080`,
creates an organisation, and runs `examples/mcp_client.rs` (the `rmcp` SDK's
OAuth client) through discovery, dynamic registration, PKCE authorization
(playing the browser with `curl` and reading the login code from the `log`
provider), token exchange, a refresh, every tool, and revocation.

```sh
cargo build -p happy-enterprise --bins --examples && scripts/mcp-client-demo.sh
```
